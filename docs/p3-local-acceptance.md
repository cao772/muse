## 事项提示边界

`uv run --extra stt muse-attention --cycles 2 --interval 5` 提供有界只读检查，输出数量/候选 ID，不输出事项正文和令牌。

Voice 服务每 15 秒读取快照，通过现有 USB 心跳传递数量；圆屏只在 Ready 显示 `Items needing you: N`。录音、思考、播放期间隐藏，CAO 不可达及 Host 心跳失效时清除。没有弹窗、自动播报、微信发送、任务执行或自动恢复旧 Codex 会话。

首次快照建立静默基线，稳定 ID 去重；专注/勿扰观察抑制新候选，截断快照不误判事项消失。去重状态仅在进程内，重启重新建立静默基线。

CAO 当前接口只有数据库快照，不能证明 Host 的实时新鲜度；屏幕数量表示“已记录待处理事项”，不能当成实时紧急告警。尚不启用根据候选 ID 的主动打断。查询“现在 Codex 等什么”直接读取该快照，不让 LLM 猜测等待状态。

## 首轮实体板与播放修复

用户确认回答内容不错，但分段播放有停顿。首轮日志证实 GPT 语音播放成功：STT 0.623s，LLM 26.045s，TTS 8.672s，8 段播放 31.674s，导出后首音 36.467s，按钮至首音 50.819s。只有这一轮有完整日志，不据此宣称三句都通过。

修复把 TTS 片段按原样 PCM 合并为最大 5 秒播放块，减少短句上传间隙；USB 使用四帧有界窗口，每个原有 768 字节帧仍逐一核对 ACK，最后仍验证 SHA-256。音色/音量和播放协议字段不变。减少间隙不等于全双工无缝流式播放；用户已试听固定长句，确认“好很多”。四帧实测最初超过原 2 KB RX 缓存导致第三帧 ACK 超时；将接收缓存改为 8 KB 后，完整三块均通过。10.32 秒 PCM，原 4 个 TTS 短段合并成 3 块，实际播放链路总耗时 13.997 秒；两个满 5 秒块的上传耗时分别 1.708 / 1.695 秒，剩余 0.32 秒块上传 0.107 秒。仍存在逐块上传间隔，不能宣称完全无缝。最终 app 重新烧录、hash 校验成功。屏幕提示尚无明确用户确认。
